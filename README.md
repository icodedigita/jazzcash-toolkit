# @icodedigita/jazzcash

**Accept JazzCash payments in your JavaScript app: install, run the setup wizard, done.**

> Unofficial. Built by developers for developers. Not affiliated with or endorsed by JazzCash.
>
> **By ICODEDIGITA.** Built for the Pakistani developer community, to help fellow developers and companies.

## Why this exists

Integrating the JazzCash Payment Gateway is harder than it should be. The guides are spread across many PDFs and pages. The secure-hash rules read slightly differently in each document. Field lists are strict: leave out one empty `""` field or sign a value differently and the gateway rejects the hash (the sandbox answers `110 Please provide a valid value for pp_SecureHash`). Amounts must be multiplied by 100, dates must be in Pakistan time, IPN and status inquiry are expected, and when something goes wrong you get a bare numeric code.

We went through that ourselves. Instead of every business writing, debugging and certifying the same integration again, we decided to make it easier for the developers and companies who come next. This project does the hard parts once, in one tested place, and a setup wizard walks you through the rest.

## What you get

- **Setup wizard (browser GUI).** `npx @icodedigita/jazzcash-setup` detects your framework, asks for your credentials step by step, updates your `.env` without touching your other variables (with a backup), and creates the route files. Re-run it any time to change values (`edit`).
- **Correct signing, always.** Secure hash generation and response verification follow the gateway's swagger. There is no "skip the hash" switch.
- **Dynamic fields.** `pp_ReturnURL`, `pp_TxnRefNo`, dates (PKT, +1 day), the x100 amount, and the phone number (mapped to `pp_MobileNumber`, `pp_MSISDN`, `ppmpf_1` or `pp_CustomerMobile` as each endpoint needs) are filled for you. `explain()` shows every field and where its value came from.
- **Payment methods:** hosted checkout (card, mobile account, voucher), MWallet REST v2.0 with CNIC, voucher create/expire, wallet linking and pay-by-token (v4), Apple Pay and Google Pay server endpoints.
- **Also handled:** IPN listener (REST), status inquiry (v1/v2), refunds (card v1/v2, wallet, Apple Pay, Google Pay).
- **Plain-language errors.** Every gateway response code is mapped to Completed / Pending / Failed / Dropped / Unknown with a customer-friendly message.
- **Test Lab (in the wizard).** Run the whole integration from the GUI: signing self-test, wallet payments, failure codes, status, vouchers, refunds, wallet linking, hosted-page checks, IPN round trip and more. Works against the simulator with no account, or your sandbox. Each result explains what it proves and what to do if it fails, and you can copy a secret-free report for JazzCash support.
- **Test-mode console messages.** In simulate/sandbox the server prints a clear "TEST MODE" notice and a one-line diagnostic with a plain-language hint for every failed gateway call; the checkout component shows a test banner and logs the same in the browser console (F12). All of it is off in live mode (and `JAZZCASH_DEBUG=0` silences it).
- **n8n nodes** so no-code automations can take payments and react to IPNs.
- **Local simulator.** `npx @icodedigita/jazzcash-setup simulate` runs a stand-in gateway driven by the public sandbox test data (mobile numbers, test cards, wallet linking, tokens). It checks your hash like the real gateway and can deliver IPNs. No JazzCash account needed.
- **Checkout components** for React: card, mobile account, voucher, Apple Pay, Google Pay.
- **Types and validation generated from the gateway's swagger** so required fields and allowed values match the source.

## Quick start (Next.js)

```bash
npm i @icodedigita/jazzcash-next
npx @icodedigita/jazzcash-setup      # opens the wizard in your browser
```

1. Pick the features you need.
2. Paste your Merchant ID, Password and Integrity Salt (JazzCash portal: *Integration → Credentials*).
3. Confirm your Return URL and IPN URL.
4. Review the `.env.local` changes and the sample request, press **Apply**, then **Send test payment**.

The wizard writes this file for you. You can also write it by hand:

```ts
// app/api/jazzcash/[...jazzcash]/route.ts
import { createJazzCashRoutes } from '@icodedigita/jazzcash-next';

export const { GET, POST } = createJazzCashRoutes({
  onPaid: async (txn) => { /* mark the order paid. Safe to run twice (IPN retries) */ },
  onFailed: async (txn) => {},
  onPending: async (txn) => {},   // vouchers are paid later
  successUrl: '/payment/success',
  failureUrl: '/payment/failed',
  pendingUrl: '/payment/pending',
  // REQUIRED in live mode: the server decides the price, never the browser
  resolveOrder: async (body) => ({ amount: await priceFor(body.orderId), orderId: String(body.orderId) }),
  // status and refund routes stay closed until you add this
  authorize: async (req) => isAdmin(req),
});
```

```tsx
'use client';
import { JazzCashCheckout } from '@icodedigita/jazzcash-next/client';

<JazzCashCheckout amount={1500} orderId="ORDER1001" methods={['card', 'wallet', 'voucher']} />
```

The routes this one file serves: `checkout`, `wallet`, `voucher`, `link-wallet`, `applepay/session`, `applepay/pay`, `googlepay/pay`, `callback` (Return URL), `ipn`, and the protected `status`, `refund`, `token-pay`, `token-inquiry`, `token-delete`, `voucher-expire`, `link-account`.

### Other frameworks
Run the same wizard. SvelteKit, Nuxt, Remix and Astro get a single route file that wraps `createJazzCashHandler` from the core package. Vite, Expo and React Native get `server/jazzcash-server.mjs` (Express). Express projects use `app.use('/api/jazzcash', jazzCashExpress({ ... }))`.

## Test mode, the console and the Test Lab

When `JAZZCASH_MODE` is `simulate` or `sandbox` you will see this once in your server terminal:

```
[JazzCash toolkit v0.1.0 by ICODEDIGITA] TEST MODE (JazzCash sandbox): no real money moves. Developer details for every gateway call are printed in this terminal (and in the browser console, press F12). ...
```

Every gateway call then logs a line, and failures add a hint:

```
[JazzCash sandbox] mwalletV2 [T2026...] -> 999 Access denied. You are not permitted to perform this transaction.
    hint: Credentials and signing are fine (the gateway answered). This merchant is not enabled for this payment method yet ...
```

In the browser the checkout shows a "Test mode" banner and prints the same hints to the console. In sandbox, a hosted-checkout request for a payment type your merchant is not enabled for is caught on your server with a clear message (HTTP 422) instead of ending on a JazzCash error page. Nothing is logged or shown like this in live mode, and no secret is ever logged.

**Test Lab:** `npx @icodedigita/jazzcash-setup` → *Test lab* tab. Pick simulate (no account) or sandbox and press **Run all checks**. Results are *pass*, *fail*, or *blocked by merchant setup* (JazzCash has not enabled that method for your Merchant ID, which is not an integration error). The hosted-checkout buttons open the payment page in a new tab and bring you back to a result page that verifies the hash.

## Configuration

| Variable | Meaning |
|---|---|
| `JAZZCASH_MODE` | `simulate`, `sandbox` or `live` |
| `JAZZCASH_MERCHANT_ID` | your Merchant ID |
| `JAZZCASH_PASSWORD` | your gateway password |
| `JAZZCASH_INTEGRITY_SALT` | your Integrity Salt (surrounding whitespace is trimmed) |
| `JAZZCASH_MPIN` | merchant MPIN, only for refunds |
| `JAZZCASH_SITE_URL` | public origin of your site, used to build the Return URL |
| `JAZZCASH_RETURN_URL` | optional explicit Return URL. Must match the one in your JazzCash profile **exactly** |
| `JAZZCASH_BASE_URL` | optional override of the gateway base URL |
| `JAZZCASH_ALLOWED_HOSTS` | live mode only: hosts allowed to be used when deriving the Return URL from the request |

Sandbox and production use the same gateway URL; which one you reach is decided by your credentials.

## Testing without a JazzCash account

```bash
npx @icodedigita/jazzcash-setup simulate     # http://127.0.0.1:4455, control panel at /__sim
```
Set `JAZZCASH_MODE=simulate`. The panel lets you force the next outcome (insufficient balance, wrong MPIN, expired, ...), send IPNs, and mark vouchers paid. Test data: mobile `03123456789` + CNIC `345678` succeeds; other numbers produce the documented failures; card expiry `01/39` approves, `05/39` declines, `04/27` expired card, and so on; wallet linking uses OTP `123456` and MPIN `1234`.

In code, for your CI: `import { createSimulator } from '@icodedigita/jazzcash/simulator'`.

The simulator refuses to start, and `simulate` mode refuses to load, when `NODE_ENV=production`.

## Things that trip people up (handled for you)

- Amounts are sent as the value x100 (`Rs 1` → `"100"`).
- Dates use `YYYYMMDDHHmmss` in Pakistan time (UTC+5); expiry is +1 day.
- `pp_TxnRefNo` must be unique. `pp_BillReference` allows letters and digits only.
- Empty fields stay `""`. Only non-empty fields whose names start with `pp` are hashed, sorted by name, joined with `&`, prefixed with the salt, encoded ISO-8859-1, HMAC-SHA256 with the salt as key, uppercase hex.
- Text outside ISO-8859-1 (for example Urdu in `pp_Description`) cannot be signed. It is rejected with a clear error instead of producing a hash the gateway rejects.
- `000` on a status inquiry means the *inquiry* worked. A payment is paid only when the payment code is `121` and the status is `Completed`.
- Vouchers are paid later at an agent: a payment can be pending first and paid later (IPN). IPNs carry no amount, so look the amount up from your own order by `txnRefNo`.
- The hosted page returns the customer to the Return URL by POST. The route verifies the hash before anything else.

## n8n

Install the community node in n8n (*Settings → Community Nodes → Install*: `@icodedigita/n8n-nodes-jazzcash`), then add a **JazzCash API** credential (environment, Merchant ID, Password, Integrity Salt, optional MPIN and Return URL).

- **JazzCash** node: pick a *Resource* and *Operation* and the options load in:
  - *Payment*: Create Hosted Checkout, Mobile Account Payment, Pay With Token
  - *Transaction*: Get Status, Refund
  - *Voucher*: Create, Expire
  - *Wallet*: Link Account, Get Token, Delete Token
  - *Utility*: Calculate / Verify Secure Hash, Explain Response Code, Rupees to JazzCash Amount
- **JazzCash Trigger** node: a webhook that starts a workflow on a payment notification (IPN) or when the customer returns (Return URL). The secure hash is always verified; forged calls get a 403 and start nothing. Copy the trigger's production URL into the JazzCash portal as the IPN URL (or use it as the Return URL).

Typical automation: *Webhook/Form → JazzCash: Create Hosted Checkout → send link → JazzCash Trigger (IPN) → IF paid → update sheet / send receipt*. In sandbox, outputs carry `testMode: true` and a `hint` on failures; the n8n server log shows the same TEST MODE messages. Status inquiry is also there for scheduled reconciliation of pending payments.

The nodes are covered by automated tests with mocked n8n contexts against the simulator. They have not been loaded into a running n8n instance yet.

## Going live checklist

1. Finish JazzCash onboarding (see [docs/ONBOARDING.md](docs/ONBOARDING.md)).
2. Register your Return URL and IPN URL in the portal. The IPN URL must be reachable from the internet.
3. Run the sandbox tests JazzCash asks for (mobile account, voucher, card) and send them the screenshots.
4. Add `resolveOrder` (server-side pricing) and `authorize` (for status/refund routes).
5. Switch to live credentials and `JAZZCASH_MODE=live`. Delete the `/jazzcash-demo` page.

## Security

- Secrets are read on the server only. React components talk only to your own route and never see credentials.
- Callbacks and IPNs are accepted only when the secure hash verifies; your `onPaid` hook only runs for verified data. Make it idempotent.
- In live mode the browser cannot choose its own price: `resolveOrder` is required for customer-facing routes.
- The HTTP handler never forwards raw gateway fields from the browser and never returns raw gateway responses (they can echo `pp_Password`).
- Status, refund, token and voucher-expire routes answer `403` until you provide `authorize`.
- The Return URL is derived from `JAZZCASH_SITE_URL`. In live mode the `Host` header is trusted only if listed in `JAZZCASH_ALLOWED_HOSTS`.
- The wizard listens on `127.0.0.1` only, requires a one-time token, rejects foreign `Host` headers, never sends secrets back to the page (only masked previews), and writes the env file with mode `0600`. `.env.local` and its backup are added to `.gitignore`.
- Card details never touch your server in the hosted flow.
- **By JazzCash's design the hosted-checkout form carries `pp_Password`** (it is in the official PHP sample too), so it reaches the customer's browser. It is the gateway password, not the Integrity Salt or MPIN, which never leave your server. Treat it accordingly: use a dedicated password, do not log checkout forms (the n8n node output and your own logs included), and rotate it if it is ever exposed.

## What the real sandbox does (observed)

- A wrong signature gets **110** "Please provide a valid value for pp_SecureHash". The documented `115` also exists, so both are treated as hash failures.
- A payment method your merchant account is not enabled for gets **999 "Access denied. You are not permitted to perform this transaction."** with a valid response hash. Credentials and signing are fine in that case; ask JazzCash to enable the method for your Merchant ID.
- The hosted page answers **"Sorry! Your transaction could not be processed due to insufficient merchant information…"** (a redirect to `/payment-frontend/message/…`) when the form limits it to a payment type (`pp_TxnType` of `MPAY`, `MWALLET` or `OTC`) that your merchant account has not been set up for. With `pp_TxnType` left empty the gateway creates a normal session instead. Same root cause as "Access denied": ask JazzCash to enable the payment methods for your Merchant ID.
- A status inquiry for an unknown reference returns inquiry code `000` with payment code `999` and empty details.
- Response hashes verified against the real gateway for wallet, voucher and status responses.

## Known differences between JazzCash documents

Where the swagger, the PDFs and other pages disagree, this project follows the swagger (the final source).
- Hash message encoding is ISO-8859-1 (swagger and Features page). The sandbox hash tool and one doc say UTF-8. They are identical for ASCII.
- The older SOAP IPN described in some material is not supported. Only the REST IPN is.
- Card refund responses use keys without the `pp` prefix (`ResponseCode`, `SecureHash`). Because only `pp` fields are hashed, they cannot be verified with the documented rule, so the client reports `hashValid: null` for them.
- The Apple Pay merchant-session response carries no hash in the swagger; it is not hash-checked.

## Current status and limits

Honest list of what has and has not been verified:
- **Verified by automated tests (188):** all hash examples from the swagger, the hash doc and the Features page; PKT time, amounts, response-code mapping; every sandbox test fixture (mobile accounts, test cards by expiry, saved-card tokens, wallet linking, pay-by-token); IPN, status, refunds, vouchers; Apple Pay and Google Pay request building; the HTTP handler's security behaviours; the wizard server (token, host check, env merge, file creation).
- **Verified end to end** in a real Next.js 15 dev server with the packed packages: wizard → generated route → checkout → hosted page (simulator) → callback → paid hook; forged callback rejected; voucher → IPN → paid hook.
- **Partly verified against the real JazzCash sandbox** (signing, response hashes, hosted-page session creation, the "Access denied" and "insufficient merchant information" behaviours). A full successful payment was not seen because the test merchant had no payment methods enabled yet. The simulator follows the public test data and the swagger, but the real gateway can differ (for example the exact mapping of card-expiry outcomes to response codes is an assumption).
- **Apple Pay / Google Pay:** server side built from the swagger and exercised against the simulator. The browser buttons are untested in real browsers/devices and need Apple domain verification / the Google tokenization settings JazzCash provides.
- **SvelteKit, Nuxt, Remix, Astro** route templates and the **Express** backend for Vite are generated but have not been run inside those frameworks yet.
- **React Native:** `JazzCashWebView` and its helpers are built and the helpers are unit-tested, but the component itself has not been run on a device or simulator.
- Direct card API (authorize/capture/void/pay), 3DS authentication, card tokenization APIs, MWallet v3 (hosted MPIN), BNPL / PayFast refunds and balance inquiry are not included.

## React Native / Expo

```tsx
import { JazzCashWebView } from '@icodedigita/jazzcash-react-native';

<JazzCashWebView
  endpoint="https://api.example.com/api/jazzcash"   // your backend (never the JazzCash URL)
  siteUrl="https://api.example.com"                  // the backend's JAZZCASH_SITE_URL
  paths={{ success: '/payment/success', failure: '/payment/failed', pending: '/payment/pending' }}
  order={{ orderId: 'ORDER1001' }}
  onResult={(r) => console.log(r.status, r.ref, r.code)}   // 'completed' | 'pending' | 'failed' | 'invalid'
/>
```
The paths must equal the `successUrl`/`failureUrl`/`pendingUrl` you gave the server route. The component intercepts the redirect, so those pages do not need to exist.
